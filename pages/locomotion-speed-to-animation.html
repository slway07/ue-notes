Locomotion ① 속도가 애니메이션이 되는 길

캐릭터가 움직이는 것과 애니메이션이 도는 것은 별개다. 둘을 잇는 값은 Speed 와 Direction 둘뿐이다.

캐릭터가 앞으로 나아가는 일과 다리가 움직이는 일은 서로 다른 시스템이 맡는다. 이동은 캡슐의 위치를 바꾸고, 애니메이션은 뼈를 돌린다. 그 사이를 잇는 값은 Speed 와 Direction 두 개뿐이고, AnimBP 가 매 프레임 이 둘을 계산해 BlendSpace 의 좌표로 넘긴다.

1. 캐릭터 이동과 애니메이션은 별개다

이동은 UCharacterMovementComponent 가 캡슐을 옮기는 일이다. 이 컴포넌트가 캡슐의 위치와 Velocity 를 정한다.

애니메이션은 뼈를 움직이는 일이다. 애님 그래프는 어느 뼈를 얼마나 돌릴지 계산할 뿐, 캡슐이 어디로 갔는지는 모른다. 두 시스템은 서로를 모른다.

그래서 AnimBP 가 중간에서 값을 옮긴다. 이동 컴포넌트가 남긴 Velocity 를 읽어 Speed(수평 속도의 크기)와 Direction(캐릭터가 보는 쪽 기준의 각도)으로 줄이고, 이 둘을 BlendSpace 좌표로 쓴다. 이 페이지는 그 변환과, 변환된 값이 실제로 어떻게 쓰이는지만 다룬다.

2. 값의 흐름

그림은 위에서 본 평면이다. 캐릭터는 가운데에 있고 위쪽을 본다. 캔버스를 클릭하거나 끌면 그 지점이 속도 벡터가 된다. 중심에서 멀수록 Speed 가 크고, 가장자리가 600 이다.

Speed 0~600426
Direction -180~180+39°
BlendSpace 좌표(+39, 426)

오른쪽으로 가면 Direction 이 +, 왼쪽으로 가면 − 다. 정면이 0, 뒤가 ±180 이다. 그림의 + 와 − 표시가 그 규칙을 보여 준다.

이 값이 BlendSpace 의 가로축(Direction)·세로축(Speed)으로 들어간다. 그림 오른쪽(좁은 화면에서는 아래)의 사각형은 두 값을 축에 놓아 본 것이다. 실제 샘플 배치와 삼각분할은 ③ 루트 모션과 BlendSpace 에서 다룬다.

캐릭터는 가운데에서 정면(위쪽)을 본다. 중심에서 가장자리까지가 Speed 0~600 이고, 가장자리를 넘겨 끌면 600 에서 멈춘다. 좁은 화면에서는 평면도가 위, BlendSpace 가 아래로 재배치된다.

Direction 의 부호는 어디서 정해지나

엔진에서 Direction 을 만드는 함수는 UKismetAnimationLibrary::CalculateDirection 이다. 입력은 FVector Velocity 와 FRotator BaseRotation, 출력은 도 단위 각도(-180~180)다.

  • 속도를 GetSafeNormal2D 로 수평화한다. Z 는 무시된다
  • 전방축과 내적해 FMath::Acos 로 각을 구하고 도로 바꾼다
  • 우측축과의 내적이 음수면 부호를 뒤집는다. 그래서 오른쪽은 +, 왼쪽은 − 다
  • 속도가 거의 0 이면 0 을 돌려준다

구버전 UAnimInstance::CalculateDirection 은 deprecated 다.

3. AnimBP 에서 실제로 이렇게 쓴다

2절의 Speed·Direction 은 개념이 아니라 AnimBP 가 매 프레임 실제로 계산해 변수에 담는 값이다. 블루프린트와 C++ 어느 쪽으로도 같은 일을 한다.

블루프린트 (Event Blueprint Update Animation 안)

Try Get Pawn Owner  ─ 유효성 검사
   ├→ Get Velocity ─→ Vector Length XY ──────────→ [Speed]  변수에 저장
   └→ Get Velocity ─┐
      Get Actor Rotation ─┴→ Calculate Direction ─→ [Direction] 변수에 저장

C++ (같은 일)

APawn* Owner = TryGetPawnOwner();
if (Owner)
{
    const FVector Velocity = Owner->GetVelocity();
    Speed = Velocity.Size2D();
    Direction = UKismetAnimationLibrary::CalculateDirection(Velocity, Owner->GetActorRotation());
}
  • 저장한 Speed 와 Direction 을 BlendSpace 노드의 두 축 입력에 연결한다. 세로축이 Speed, 가로축이 Direction 인 구성이 흔하다.
  • 액터(Pawn)를 직접 읽으므로 이 계산은 게임 스레드 단계에서 해야 한다. 워커 스레드 단계에서 액터를 읽으면 안 된다 — 같은 사이트의 AnimBP는 한 프레임에 무엇을 하나 페이지에 그 이유가 있다.

해 볼 것. 세 값을 기본값(2048 / 2048 / 8)에 두고 올라가는 선과 내려가는 선을 비교해 봐라. 가속과 감속 숫자가 같은데도 내려오는 쪽이 훨씬 가파르다. 기본값에서 재 보면 0 → 600 가속에 0.28초, 600 → 0 정지에 0.08초 — 같은 숫자를 넣었는데 멈추는 쪽이 3.4배 빠르다. 이제 GroundFriction 만 0 으로 내려 보면 두 선의 기울기가 같아진다. 왜 그런지는 아래에 있다.

왜 멈출 때가 더 빠른가

가속과 감속은 서로 다른 함수에서 처리된다. 가속은 단순하다.

Velocity += Acceleration * DeltaTime;        // 일정한 가속
Velocity = Velocity.GetClampedToMaxSize(MaxInputSpeed);

가속 중에도 마찰이 쓰이기는 하지만 속도의 크기를 줄이지 않는다. 엔진 주석이 그 이유를 적어 두었다 — 마찰은 방향을 바꾸는 능력에만 관여한다. 그래서 직선으로 달리는 동안 GroundFriction 을 올려도 최고 속도에 닿는 시간은 그대로다.

감속은 다르다. ApplyVelocityBraking 안에서 두 힘이 동시에 걸린다.

Friction = Friction * BrakingFrictionFactor;                  // 기본 8.0 x 2.0 = 16
Velocity = Velocity + ((-Friction) * Velocity + RevAccel) * dt;
  • RevAccel 은 BrakingDecelerationWalking 만큼의 일정한 감속이다 (기본 2048)
  • 거기에 속도에 비례하는 -Friction x Velocity 가 더해진다. 빠를수록 더 세게 잡아당긴다
  • BrakingFrictionFactor 기본값이 2.0 이라 GroundFriction 8.0 은 실제로 16 으로 쓰인다. 엔진 주석은 이 값을 "historical value" 라고 적고 있다

600cm/s 로 달리다 입력을 떼는 순간을 숫자로 보면 이렇다. 마찰 항이 16 x 600 = 9600, 여기에 고정 감속 2048 을 더해 합이 11,648cm/s² 다. 가속은 2048 뿐이었다. 같은 숫자를 넣어도 멈추는 쪽이 대여섯 배 강하다.

속도가 10cm/s(BRAKE_TO_STOP_VELOCITY) 아래로 내려오면 엔진이 속도를 0 으로 끊는다. 아주 느리게 영원히 미끄러지는 일이 없도록 하는 장치다.

5. 캐릭터는 어느 쪽을 보는가

캐릭터의 몸이 어느 쪽을 향하느냐에 따라 Direction 의 쓰임이 달라진다. 회전 속도 값인 RotationRate 의 기본값은 FRotator(0, 360, 0) 로, Yaw 만 초당 360 도다. 방향을 정하는 스위치는 두 개다.

bOrientRotationToMovement — 가는 쪽을 본다

이 값을 켜면 캐릭터가 가는 쪽을 본다. 몸이 진행 방향을 따라 돌기 때문에, 캐릭터 기준으로 잰 Direction 은 거의 항상 0 에 가깝게 유지된다. 앞으로만 가는 셈이다.

bUseControllerDesiredRotation — 컨트롤러가 원하는 쪽을 본다

이 값을 켜면 캐릭터가 컨트롤러가 원하는 쪽을 본다. 몸은 그 방향을 유지한 채 옆이나 뒤로도 갈 수 있으므로 Direction 이 -180~180 을 오간다. 옆걸음과 뒷걸음이 여기서 생긴다.

그래서 스트레이프가 필요한 게임은 후자를 쓰고, 이때는 Direction 축이 실제로 쓰이므로 BlendSpace 도 2D 가 필요해진다. 전자는 Direction 이 거의 0 이라 가로축이 거의 쓰이지 않는다.

그림 읽는 법

왼쪽과 오른쪽에 같은 캐릭터를 위에서 내려다본 그림이 하나씩 있다. 둘에게 똑같은 입력을 주고, 스위치만 다르게 켜 둔 것이다. 입력은 좌우로 천천히 꺾인다.

그림의 요소무엇인가
점선 화살표 (입력)스틱이나 WASD 가 가리키는 방향. 플레이어가 가고 싶은 쪽이다. 두 그림 모두 같은 각도로 움직인다
동그라미캐릭터를 위에서 본 몸통(캡슐)
동그라미에서 튀어나온 짧은 선과 점몸이 보고 있는 쪽. 사람으로 치면 코다. 이게 돌아가는 속도를 정하는 값이 RotationRate 다
맨 아래 숫자 (Direction)점선(가고 싶은 쪽)과 코(보고 있는 쪽)가 몇 도나 벌어져 있는지. 이 값이 그대로 BlendSpace 의 가로축으로 들어간다

무엇을 보면 되나. 왼쪽은 코가 점선을 쫓아간다. 둘이 거의 겹치므로 Direction 이 0 근처에 머문다 — 앞으로 걷는 애니메이션 하나로 충분하다는 뜻이다. 오른쪽은 코가 위쪽에 고정돼 있다. 조준 방향을 유지하기 때문이고, 그래서 점선만 혼자 돌고 Direction 이 −180~180 을 오간다 — 옆걸음·뒷걸음 애니메이션이 반드시 필요해진다.

360 °/s

몸이 1초에 돌 수 있는 각도. 어디 있나 — UCharacterMovementComponent 의 프로퍼티. 캐릭터 BP → CharacterMovement 컴포넌트 → 디테일 패널 Character Movement (Rotation Settings). 기본값은 FRotator(0, 360, 0) 으로 Yaw 만 360 이다.

해 볼 것. RotationRate 를 45 까지 내려 봐라. 왼쪽 캐릭터의 Direction 이 0 에 붙어 있지 못하고 출렁인다. 몸이 입력을 따라잡지 못하는 동안에는 왼쪽도 Direction 이 0 이 아니다 — 급선회할 때 옆걸음 애니메이션이 잠깐 섞이는 이유가 이것이다.
