Collision — Preset · Channel · Trace

프리셋·채널·응답으로 충돌을 거르는 법과, Line·Sweep·Overlap 트레이스를 고르는 법. 두 물체가 막히려면 왜 양쪽이 모두 Block이어야 하는지도.

1. 프리셋은 이름표가 아니라 네 값을 묶은 것이다

디테일 패널의 Collision Preset 드롭다운은 코드에서 CollisionProfileName 이고, 프리셋 목록은 UCollisionProfile 이 들고 있다. 이름만 보고 있으면 놓치지만, 프리셋 하나에는 네 가지가 들어 있다.

  • Collision Enabled — 쿼리에 닿는지, 물리로 시뮬레이션되는지
  • Object Type — 이 컴포넌트가 어떤 종류인지 (하나)
  • Response To Channels — 채널 64개 각각에 대한 Ignore / Overlap / Block
  • bCanModify — 게임이 이 프리셋을 고칠 수 있는지

컴포넌트에서 보이는 이 값들은 실제로 BodyInstance 에 들어 있다. 코드에서 BodyInstance.CollisionResponses 를 찾게 되는 이유다.

엔진 기본 프리셋은 Engine/Config/BaseEngine.ini 에 이렇게 적혀 있다.

+Profiles=(Name="BlockAll", CollisionEnabled=QueryAndPhysics,
           ObjectTypeName="WorldStatic", CustomResponses=, bCanModify=False)

CustomResponses 가 비어 있는데도 전부 Block 인 이유는, 프리셋을 읽을 때 기본 응답 컨테이너에서 시작하기 때문이다. 그 기본값은 모든 채널 Block 이다(기즈모 채널만 Ignore). 그래서 "아무것도 안 적은 프리셋"은 곧 "전부 Block" 이다.

채널IgnoreOverlapBlock

표는 64개 중 6개만 보여 준다. 나머지도 같은 규칙으로 정해진다.

프리셋을 고른 뒤 응답 하나만 바꾸면 엔진은 즉시 프리셋 이름을 Custom 으로 바꾼다. 프리셋은 "지금 값들의 이름"이지, 값을 계속 묶어 두는 잠금장치가 아니다. SetCollisionEnabled·SetObjectType·SetCollisionResponseToChannel 모두 그렇게 동작한다.

2. 채널은 64개, 그중 게임이 쓰는 것은 50개

응답 컨테이너는 채널 64개의 배열이다. 번호와 용도가 정해져 있다.

범위무엇
0~7
8개		엔진 기본 채널
WorldStatic · WorldDynamic · Pawn · Visibility · Camera · PhysicsBody · Vehicle · Destructible
8~13
6개		엔진 트레이스 채널 (숨김)
기즈모용 1번 등. 게임에서 쓰라고 열어 둔 것이 아니다
14~63
50개		게임 채널
프로젝트에서 만든 트레이스·오브젝트 채널

기본 8개 중 오브젝트 채널 6개(WorldStatic, WorldDynamic, Pawn, PhysicsBody, Vehicle, Destructible)와 트레이스 채널 2개(Visibility, Camera)가 게임에서 바로 쓰는 채널이다. 나머지 50개는 프로젝트가 트레이스용으로 만들 수도, 오브젝트용으로 만들 수도 있다.

5.8 에서 게임 채널은 50개다. 예전 기억으로 "18개" 라고 알고 있으면 프로젝트 설정 화면과 어긋난다.

새 채널을 만들 때 정하는 DefaultResponse 는 그 채널의 전 세계 기본 응답이 된다. 기본값은 Block 이라, 아무 생각 없이 채널을 추가하면 모든 프리셋이 그 채널을 Block 한다. "새 트레이스 채널을 만들었더니 온 세상이 맞는다" 는 여기서 나온다.

3. ObjectType 은 "나는 무엇인가", Channel 은 "무엇으로 검사하는가"

둘을 헷갈리는 이유는 같은 채널 목록을 쓰기 때문이다. 하지만 역할은 다르다.

정하는 것어디에 쓰나
Object Type이 컴포넌트의 정체. 하나만 고른다물리 접촉·오브젝트 쿼리에서 상대가 나를 찾는 이름
Trace Channel쿼리가 무엇을 검사하는지LineTraceSingleByChannel 같은 트레이스의 인자

WorldStatic 은 레벨 지오메트리, WorldDynamic 은 움직이는 액터에 주로 붙는 이름이다. 이름이 역할을 암시하지만, 필터 판정에 쓰이는 것은 ObjectType 비트 하나다.

그래서 "무기 트레이스가 캐릭터를 맞나?" 는 두 단계다. 무기 트레이스는 Weapon 채널로 쏘고, 캐릭터 캡슐은 Pawn 오브젝트다. 맞는지는 캡슐의 Weapon 채널 응답이 정한다. 캡슐의 ObjectType 이 Pawn 인 것은 "물리 접촉에서 상대가 나를 Pawn 으로 본다" 는 뜻이지, 트레이스 채널과는 별개다.

디테일 패널도 이 둘을 나눠 보여 준다. Object Type 은 드롭다운 하나이고, 응답은 Trace Responses 와 Object Responses 두 묶음으로 나뉜다. 채널마다 Ignore / Overlap / Block 체크박스 세 개가 붙는 구조다. 물리 접촉은 상대 ObjectType 에 대한 내 응답을, 트레이스는 내 트레이스 채널에 대한 오브젝트의 응답을 본다.

프리셋에 트레이스 채널을 ObjectType 으로 넣으면 엔진은 그 프리셋을 버리고 경고를 남긴다. ObjectType 은 오브젝트 채널이어야 한다.

4. 응답은 세 값이고, 약한 쪽이 이긴다

응답은 Ignore · Overlap · Block 셋뿐이고, enum 값이 0 · 1 · 2 순서다. 그래서 엔진은 두 응답을 비교할 때 그냥 작은 쪽을 고른다.

Ignore (0)Overlap (1)Block (2)
IgnoreIgnoreIgnoreIgnore
OverlapIgnoreOverlapOverlap
BlockIgnoreOverlapBlock

의미는 이렇다.

  • Ignore — 없는 것과 같다. 쿼리도 물리도 닿지 않는다
  • Overlap — 막지 않는다. 겹침을 알리고, 조건이 맞으면 BeginOverlap 이 뜬다
  • Block — 막는다. 물리는 접촉하고, 트레이스는 거기서 멈춘다

5. 두 물체가 막히려면 양쪽이 모두 Block 이어야 한다

물리 접촉의 판정은 Chaos 필터에 이렇게 들어 있다.

const bool bBlocking =
    (A.ChannelMask & B.BlockMask) &&
    (B.ChannelMask & A.BlockMask);

BlockMask 는 그 물체가 Block 하기로 한 채널들의 비트 묶음이다. 식을 풀면 A 가 B 의 타입을 Block 하고, B 도 A 의 타입을 Block 해야 막힌다. 한쪽이라도 Overlap 이면 막히지 않고, 한쪽이라도 Ignore 면 아예 없는 것과 같다.

A
B

해 볼 것. A 를 Block, B 를 Overlap 으로 두라. 둘은 막히지 않고 통과한다. 이제 B 도 Block 으로 바꾸면 부딪혀 멈춘다. 한쪽만 Block 해서는 막히지 않는다는 것이 이 그림의 요점이다.

6. 트레이스는 왜 한쪽만 보는 것처럼 느껴지나

트레이스도 원칙은 같다. 엔진은 쿼리 쪽 응답과 맞은 오브젝트 쪽 응답을 모두 보고 작은 쪽을 고른다. 그런데 쿼리 쪽 응답의 기본값이 전부 Block 이다.

LineTraceSingleByChannel(..., TraceChannel,
    Params, ResponseParam = FCollisionResponseParams::DefaultResponseParam)

// FCollisionResponseParams 의 기본 생성자
FCollisionResponseParams(ECollisionResponse DefaultResponse = ECR_Block)

그래서 평소에는 맞은 오브젝트의 응답만 결과를 정하는 것처럼 보인다. 쿼리 쪽이 이미 전부 Block 이라 min 을 해도 오브젝트 쪽이 이기기 때문이다. 반대로 ResponseParam 을 직접 넘겨 쿼리 쪽에서 특정 오브젝트 타입을 Ignore 하면, 오브젝트가 Block 이어도 맞지 않는다.

기본 Pawn 프리셋이 Visibility 만 Ignore 인 이유가 여기 있다. 캐릭터 캡슐은 물리로는 단단히 막히지만, 카메라·조준 트레이스는 그 캡슐을 통과한다. 조준선이 캐릭터 몸에 걸리면 불편하기 때문이다.

7. 트레이스의 모양과 개수

트레이스 함수 이름은 길지만 규칙이 있다. LineTraceSingleByChannel 을 쪼개면 모양(Line) · 개수(Single) · 필터(ByChannel)다. 이 세 축만 알면 이름이 외워진다.

축값이름에 이렇게 나온다
모양Line · Sweep · OverlapLineTrace… · Sweep… · Overlap…
개수Single · Multi · Test…Single… · …Multi… · …Test…
필터Channel · ObjectType…ByChannel · …ByObjectType

모양 — 라인은 부피가 없고, 스윕은 있다

Line 은 점에서 점으로 가는 선이다. 부피가 없다. Sweep 은 구·캡슐·박스를 끌고 가는 것이라, 선이 지나갈 수 있는 틈도 막힌다. Overlap 은 이동 없이 어떤 위치에 모양을 겹쳐 보는 것이다.

28

해 볼 것. 반지름을 0 으로 두면 라인이다. 구멍을 그대로 지나간다. 반지름을 22 이하로 두면 스윕도 통과하고, 넘기면 벽 모서리에 걸린다. 같은 시작점·끝점인데 결과가 갈린다.

스윕에는 모양과 회전이 함께 간다. 박스는 회전에 따라 막히는 범위가 달라지므로 FQuat 인자가 붙는다. 캐릭터 이동에 쓰는 캡슐 스윕이 대표적이다.

개수 — Single · Multi · Test

같은 경로라도 몇 개를 돌려주나가 다르다. 아래 그림의 앞 두 상자는 Overlap, 마지막은 Block 이다.

개수함수 (Line · Sweep · Overlap)
SingleLineTraceSingleByChannel · SweepSingleByChannel · Overlap 없음
MultiLineTraceMultiByChannel · SweepMultiByChannel · OverlapMultiByChannel
TestLineTraceTestByChannel · SweepTestByChannel · OverlapAnyTestByChannel

Single 은 Overlap 을 무시한다. 엔진이 Single·Test 에서는 bIgnoreTouches 를 강제로 켜기 때문이다. 첫 Block 만 FHitResult 로 돌려주고, 맞은 것이 Overlap 뿐이면 결과가 비어 있다. Multi 는 Overlap 도 모은다. 대신 Block 을 만나면 그 뒤로는 보지 않는다. Test 는 bool 만 돌려준다 — 어디에 맞았는지, 몇 개 맞았는지는 알려 주지 않는다. 가장 싸다.

8. Channel 로 쏘나, ObjectType 으로 쏘나

거르는 방식도 둘이다. ByChannel 은 채널 하나를 정하고 오브젝트의 응답을 본다. ByObjectType 은 오브젝트 타입 여러 개를 정하고 그 타입인지만 본다.

ByChannelByObjectType
고르는 것채널 하나 (ECC_Visibility 등)오브젝트 타입 여러 개 (ECC_Pawn, ECC_Vehicle …)
응답본다안 본다 — 타입이 맞으면 맞는다
쿼리 응답FCollisionResponseParams없다
대표 함수LineTraceSingleByChannelLineTraceSingleByObjectType
쓰는 곳무기·카메라처럼 오브젝트의 필터 정책을 존중해야 할 때"Pawn·Vehicle 만" 같은 타입 스캔
 
// 채널 쿼리 — 오브젝트의 응답을 존중한다
World->LineTraceSingleByChannel(Hit, Start, End, ECC_Visibility, Params);

// 오브젝트 타입 쿼리 — 타입만 본다
FCollisionObjectQueryParams ObjParams(FCollisionObjectQueryParams::AllDynamicObjects);
ObjParams.AddObjectTypesToQuery(ECC_Pawn);
World->LineTraceSingleByObjectType(Hit, Start, End, ObjParams, Params);
오브젝트 타입 쿼리는 응답을 보지 않는다. Chaos 필터의 ObjectTypeNarrowFilter 는 쿼리 타입 마스크와 오브젝트의 채널 비트만 비교한다. 그래서 모든 채널을 Ignore 로 둔 오브젝트도 타입이 맞으면 오브젝트 타입 쿼리에는 맞는다. Collision Enabled(쿼리 트리에 있나)와 무시 목록은 여전히 적용된다.

반대로 채널 쿼리는 6절의 규칙을 그대로 따른다. 오브젝트의 응답과 쿼리 쪽 응답의 min 이 결과를 정한다.

9. Query Params — 무엇을 켜고 끄나

트레이스에 함께 넘기는 FCollisionQueryParams 가 세부 규칙을 정한다. 자주 쓰는 것만 추려도 이만큼이다.

  • bTraceComplex 기본 false
    Complex(삼각형) 충돌을 쓸지. Simple vs Complex 는 별도 문서에서 다룬다
  • bFindInitialOverlaps 기본 true
    시작점이 이미 겹쳐 있으면 bStartPenetrating 으로 알려 줄지
  • bReturnPhysicalMaterial 기본 false
    Hit.PhysMaterial 을 채울지
  • bReturnFaceIndex 기본 false
    Complex 히트의 FaceIndex 를 채울지
  • bIgnoreBlocks · bIgnoreTouches 기본 false
    Block 결과·Overlap 결과를 각각 버릴지
  • bSkipNarrowPhase 기본 false
    Overlap 에서 정밀 검사를 생략. 빠르지만 정확도가 떨어진다
  • MobilityType 기본 Any
    Static / Movable 만 대상으로 할지
  • TraceTag 기본 None
    Collision Analyzer 에서 이 쿼리를 찾는 이름표
  • AddIgnoredActor · AddIgnoredComponent
    자기 자신·무기·쉴드 등을 결과에서 뺀다

응답과 오브젝트 타입은 파라미터가 아니라 따로 넘기는 인자다. FCollisionResponseParams(쿼리 쪽 응답, 기본 전부 Block)와 FCollisionObjectQueryParams(오브젝트 타입 목록)가 그것이다.

FCollisionQueryParams Params(SCENE_QUERY_STAT(WeaponTrace), false, GetOwner());
Params.bReturnPhysicalMaterial = true;
Params.AddIgnoredComponent(ShieldComp);

FHitResult Hit;
GetWorld()->LineTraceSingleByChannel(Hit, Start, End, ECC_Visibility, Params);

FCollisionQueryParams 에는 "나 자신을 무시" 하는 플래그가 따로 없다. 생성자에 무시할 액터를 넘기거나 AddIgnoredActor 를 쓴다.

10. Hit Result — 어디를 봐야 하나

FHitResult 는 필드가 많다. 전부 외울 필요는 없고, Location 과 ImpactPoint 를 구분하는 것부터 시작하면 된다.

  • bBlockingHit
    Block 으로 맞았나. false 면 Overlap/touch 이거나 안 맞은 것
  • Time
    경로 위 어디인지 0~1. 시작이 0, 끝이 1
  • Distance
    시작점에서 Location 까지의 거리(월드 단위). 시작이 겹쳐 있으면 0
  • Location
    모양의 중심이 닿는 위치. 라인이면 충돌 지점과 같다
  • ImpactPoint
    모양의 표면이 실제로 닿은 지점. 데칼은 보통 이걸 쓴다
  • Normal · ImpactNormal
    스윕 모양 기준 노멀 · 맞은 표면의 노멀. 라인에서는 둘이 같다
  • TraceStart · TraceEnd
    요청한 시작·끝. 맞은 지점이 아니다
  • bStartPenetrating · PenetrationDepth
    시작부터 겹쳐 있었나, 빠져나오려면 얼마나 움직여야 하나
  • Component · GetActor() · BoneName
    맞은 컴포넌트·액터·본
  • PhysMaterial
    bReturnPhysicalMaterial 를 켜야 채워진다
  • FaceIndex
    Complex 히트의 삼각형 번호. bTraceComplex·bReturnFaceIndex 가 필요
스윕에서 Location 을 데칼 위치로 쓰면 어긋난다. Location 은 구 중심이 멈춘 자리이고, 표면에 붙는 점은 ImpactPoint 다. 시작이 겹쳐 있으면 Time·Distance 가 0 이고 ImpactPoint 는 Location 과 같아진다 — 의미 있는 접점이 하나가 아니기 때문이다.

11. 실전 패턴 네 가지

같은 트레이스라도 목적에 따라 모양·개수·필터가 달라진다.

조준 — 라인 하나, 첫 Block

FHitResult Hit;
FCollisionQueryParams Params(SCENE_QUERY_STAT(Aim), false, GetOwner());
if (GetWorld()->LineTraceSingleByChannel(Hit, Start, End, ECC_Visibility, Params))
{
    SpawnDecal(Hit.ImpactPoint, Hit.ImpactNormal);
}

근접 공격 — 구 스윕

FCollisionShape Shape = FCollisionShape::MakeSphere(40.f);
FHitResult Hit;
if (GetWorld()->SweepSingleByChannel(Hit, Start, End, FQuat::Identity,
        ECC_Visibility, Shape, Params))
{
    // Hit.bStartPenetrating 이면 이미 겹친 채로 시작한 것
}

트리거 — Overlap 멀티

TArray<FOverlapResult> Overlaps;
FCollisionObjectQueryParams ObjParams(FCollisionObjectQueryParams::AllDynamicObjects);
GetWorld()->OverlapMultiByObjectType(Overlaps, Pos, FQuat::Identity, ObjParams,
        FCollisionShape::MakeSphere(300.f), Params);

Overlap 결과에는 ImpactPoint·Normal 이 없다. 위치·노멀이 필요하면 스윕을 써야 한다. FOverlapResult 는 컴포넌트·아이템 인덱스·bBlockingHit 정도만 준다.

이동 — 캡슐 스윕

FCollisionShape Capsule = FCollisionShape::MakeCapsule(Radius, HalfHeight);
FHitResult Hit;
if (GetWorld()->SweepSingleByChannel(Hit, Start, End, Rot, ECC_Pawn, Capsule,
        MoveParams, FCollisionResponseParams::DefaultResponseParam))
{
    // Hit.ImpactNormal 을 따라 미끄러지게 한다
}

이동은 라인으로 하면 벽 모서리에 걸리고, 캡슐로 하면 부드럽게 미끄러진다. 그래서 캐릭터 이동은 캡슐 스윕이 기본이다.

12. Collision Enabled — 쿼리 트리와 시뮬레이션 트리

응답이 "무엇과 부딪히나" 라면, Collision Enabled 는 "어느 트리에 들어가나" 다. 충돌 데이터는 쿼리용 트리와 시뮬레이션용 트리로 나뉘어 있고, Enabled 가 어느 쪽에 넣을지 정한다.

값쿼리물리
NoCollision
장식. 가장 싸다		✗✗
QueryOnly
트리거, 총알 판정, 캐릭터 캡슐		✓✗
PhysicsOnly
흔들리는 장식. 트레이스에 안 맞는다		✗✓
QueryAndPhysics
일반 액터·월드 지오메트리		✓✓

5.8 소스에는 ProbeOnly 와 QueryAndProbe 도 있다. 물리적으로 반응하지 않으면서 접촉 데이터만 받고 싶을 때 쓰는 상태다.

두 컴포넌트의 Enabled 도 서로 맞아야 한다. 엔진은 둘의 교집합을 낸다. 예를 들어 QueryOnly 와 PhysicsOnly 가 만나면 NoCollision 이 되어 아무 일도 일어나지 않는다. 한쪽이 쿼리만, 다른 쪽이 물리만 켜 두면 서로 다른 트리에 있어 만날 일이 없다.

오버랩 이벤트는 쿼리로 계산된다. 그래서 PhysicsOnly 인 컴포넌트는 아무리 겹쳐도 BeginOverlap 이 뜨지 않는다.

13. Overlap 이벤트는 세 조건이 모두 맞아야 뜬다

엔진이 오버랩을 갱신하는 코드는 이렇다. 세 조건이 다 보인다.

if (GetGenerateOverlapEvents() && IsQueryCollisionEnabled())   // 내 쪽
{
    Params.bIgnoreBlocks = true;                              // Block 은 오버랩이 아니다
    ComponentOverlapMulti(...);

    for (...)
        if (HitComp->GetGenerateOverlapEvents())             // 상대 쪽
            ...
}
  1. 나에게 쿼리 충돌이 켜져 있고 Generate Overlap Events 가 켜져 있다
  2. 상대도 Generate Overlap Events 가 켜져 있다
  3. 두 응답의 min 이 Overlap 이다 (Block 이면 Hit, Ignore 면 아무것도 아니다)

Generate Overlap Events 의 기본값은 true 다. 그래서 "오버랩이 안 뜬다" 는 대부분 응답이나 Enabled 문제다. Block 쌍으로 만들어 놓고 오버랩을 기대하는 경우도 많다 — Block 은 Hit 이벤트이지 BeginOverlap 이 아니다.

15. 커스텀 채널·프리셋은 ini 에 저장된다

Project Settings 의 Collision 페이지에서 채널과 프리셋을 만든다. 저장되는 곳은 DefaultEngine.ini 의 [/Script/Engine.CollisionProfile] 이다.

[/Script/Engine.CollisionProfile]
+DefaultChannelResponses=(Channel=ECC_GameTraceChannel1,
    DefaultResponse=ECR_Ignore, bTraceType=True, bStaticObject=False,
    Name="Weapon")

+Profiles=(Name="MyTrigger", CollisionEnabled=QueryOnly,
    ObjectTypeName="WorldDynamic",
    CustomResponses=((Channel="Pawn", Response=ECR_Overlap)),
    HelpMessage="Pawn 만 받는 트리거")
  • bTraceType=True 면 트레이스 채널, False 면 오브젝트 채널이다. 같은 50개 슬롯을 나눠 쓴다
  • DefaultResponse 는 그 채널의 전 세계 기본 응답이다. 여기를 Ignore 로 두면, 아무 프리셋도 그 채널을 기본으로 막지 않는다. 그래서 커스텀 트레이스 채널은 Ignore 로 시작해, 필요한 프리셋에서만 Block·Overlap 으로 켜는 경우가 많다
  • +Profiles 는 게임 프리셋 추가, EditProfiles 는 엔진 프리셋 덮어쓰기다
  • 엔진 프리셋은 bCanModify=False 라 그 자리에서 고칠 수 없다. 고치면 Custom 이 된다
  • 이름을 바꾸면 ProfileRedirects·CollisionChannelRedirects 로 옛 이름을 새 이름에 연결한다

코드에서는 SetCollisionProfileName("MyTrigger") 로 통째로 적용하고, SetCollisionResponseToChannel(ECC_GameTraceChannel1, ECR_Ignore) 처럼 한 채널만 바꿀 수도 있다. 후자를 쓰면 프리셋 이름이 Custom 으로 바뀐다.

16. 안 될 때 보는 곳

  • show Collision — 콜리전 형상을 그린다. show CollisionPawn·show CollisionVisibility 는 그 채널 기준으로 보여 준다
  • Collision Analyzer — 실행 중에 발생한 쿼리를 채널·응답과 함께 기록한다

증상별로 먼저 볼 것.

증상먼저 볼 것
트레이스가 안 맞는다그 오브젝트의 트레이스 채널 응답이 Ignore 인지. 채널을 잘못 골랐는지
물리로 안 막힌다양쪽 다 Block 인지. 한쪽이 Overlap·Ignore 인지. Enabled 가 QueryOnly 인지
BeginOverlap 이 안 뜬다응답이 Block 인지(그럼 Hit), 양쪽 Generate Overlap Events, 쿼리 충돌 여부
새 채널이 온 세상을 맞는다그 채널의 DefaultResponse 가 Block 인지
프리셋을 골랐는데 값이 다르다프리셋 이름이 Custom 인지. 한 필드라도 만졌으면 프리셋은 풀린다

충돌은 에러 없이 조용히 안 되는 쪽에 가깝다. 응답 한 칸, 체크박스 하나가 원인인 경우가 대부분이라, 로그보다 매트릭스를 먼저 보는 편이 빠르다.

한 문장으로. 프리셋은 ObjectType · Enabled · 채널 64개의 응답을 묶은 이름이다. 물리 접촉은 양쪽 ObjectType 응답이 모두 Block 이어야 막히고, 트레이스는 채널 하나, 오버랩은 세 조건이다.
