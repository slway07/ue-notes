StateTree ④ — 한 틱에 얼마나 도나

"상태가 40개면 매 틱 40개를 다 보나?" — 아니다. 런타임은 활성 경로만 만진다. 이 페이지는 한 틱에 실제로 도는 것과 안 도는 것을 소스 경로로 세고, 숫자로 확인한다.

구조와 실행 노드 4종 전이와 선택 틱 비용

1. 한 틱에 실제로 도는 것

FStateTreeComponent::TickComponent
  └─ FStateTreeExecutionContext::Tick(dt)
       ① TickPrelude()
       ② TickUpdateTasksInternal
       ③ TickTriggerTransitions
       ④ TickPostlude()
단계무엇을 훑나비용이 비례하는 것
① 수집활성 프레임의 외부 데이터프레임 × 외부 데이터
② 평가자프레임마다 전역 평가자 전부평가자 수
② 글로벌 태스크프레임마다 전역 태스크 전부글로벌 태스크 수
② 상태 태스크활성 경로의 모든 상태의 태스크경로 길이 × 태스크
③ 전이OnTick 전이가 있는 활성 상태의 전이활성 상태 × 전이 수
③ 조건검사한 전이의 조건 전부 (단락 없음)전이 수 × 조건 수
③ 선택전이가 발동할 때만 — 자식 후보후보 수 × 조건

②에서 리프만 도는 게 아니다. Root → Combat → Melee 가 활성이면 세 상태의 태스크가 모두 Tick 을 받는다. 상위 상태에 붙인 태스크도 매 틱 돈다.

2. 한 틱에 안 도는 것

이쪽이 더 중요하다. "왜 40개 상태인데 안 느려지지?"의 답이 여기에 있다.

안 도는 것언제 도나
비활성 상태의 태스크·전이·조건그 상태가 활성 경로에 들어올 때만
완료 전이(OnStateCompleted)상태가 실제로 완료될 때 한 번
진입 조건(Enter Conditions)상태를 고를 때. 이미 활성이면 안 본다
고려사항(Consideration)유틸리티로 자식을 고를 때만
이벤트 전이(OnEvent)이벤트 큐에 그 태그가 있을 때만
태스크 TickbShouldCallTick 이고 실행 중일 때만
전부수면 상태면 컴포넌트 틱 자체가 꺼져 있다

그래서 "전체 상태 수"는 런타임 틱 비용에 거의 영향이 없다. 영향을 주는 것은 ① 활성 경로의 길이, ② 그 경로에 붙은 태스크 수, ③ 매 틱 검사하는(OnTick) 전이와 조건 수다. 전체 상태 수는 에셋 크기·컴파일 시간·선택 후보 수에 영향을 준다.

3. 실제 예시 — 경비 AI 하나

Root · 평가자 2 · 전역 태스크 1 ├ Idle · Wait ├ Patrol · MoveTo, Wait ├ Combat (Group) │ ├ Melee · MoveTo, FaceTarget, Attack │ └ Ranged · MoveTo, Aim, Fire └ Flee · MoveTo, Wait

지금 활성 경로가 Root › Combat › Melee 라고 하자. 이때 한 틱에 일어나는 일을 세면 이렇다.

단계값횟수
전역 평가자Distance, Health2
전역 태스크UpdateThreat1
상태 태스크0 + 0 + 33
OnTick 전이2 + 1 + 03
전이 조건전이마다 1개3
완료 전이이번 틱 없음0

합쳐서 사용자 콜백 6회 + 전이 검사 3회 + 조건 평가 3회 = 12회다. 같은 트리에 상태가 40개로 늘어도, 활성 경로가 여전히 3단이고 태스크·전이가 그대로면 이 숫자는 똑같다. 나머지 37개 상태는 배열에 있을 뿐 이번 틱에 읽히지 않는다.

직접 확인. StateTree Debugger 나 stat StateTree 로 한 틱의 TickTasks·TriggerTransition 횟수를 보라. 상태를 20개 더 넣어도 이 수치는 그대로이고, 활성 경로에 상태를 하나 더 붙이거나 OnTick 전이를 하나 더 달 때만 올라간다.

4. 시뮬레이션 — 무엇이 비용을 늘리나

3단
1개/상태
1개/상태

해 볼 것. 비활성 37개 추가를 눌러 보라. 막대가 전혀 변하지 않는다 — 그 37개는 활성 경로 밖이다. 이제 OnTick → 완료 전이를 누르면 전이·조건 막대가 0 이 된다. 매 틱 검사하던 것을 완료 시점 한 번으로 옮겼기 때문이다. 마지막으로 경로를 4단으로 올려 보라. 그때만 태스크·전이 수가 같이 늘어난다.

5. 한 틱에 전이는 몇 번까지

전이 처리는 최대 5회 반복한다. 전이 하나가 발동하면 ExitState → 선택 → EnterState 를 마치고, 다시 전이를 본다. 그래서 이벤트 하나로 상태가 두세 단계 넘어가는 일이 한 틱 안에서 일어난다.

// 최악의 한 틱
1회  Exit(Melee) → Select(Ranged) → Enter(Ranged)
2회  Exit(Ranged) → Select(Flee) → Enter(Flee)
3회  ...
5회까지. 그 뒤로는 다음 틱으로 넘어간다.

5회를 다 쓰면 그 틱은 전이 처리만 하다 끝난다. 반대로 Enter 조건이 계속 실패하면 상태를 못 정하고 다음 틱으로 넘어간다.

6. 선택이 비싼 순간

전이가 발동한 틱에만 상태 선택이 붙는다. 이때 자식 후보를 순서대로 시도하고, 후보마다 진입 조건을 검사한다. 실패하면 다음 후보로 — 최악의 경우 자식 수만큼 반복한다.

선택 방식후보 검사 횟수
TrySelectChildrenInOrder성공할 때까지. 최악 = 자식 수
TrySelectChildrenAtRandom최악 = 자식 수 (섞어서)
TrySelectChildrenWithHighestUtility자식 전부의 고려사항을 평가한 뒤 최고점
...RandomWeightedByUtility자식 전부 평가 + 가중 추첨
TryEnterState자기 자신 하나

유틸리티 방식은 매 선택마다 자식 전부를 평가한다. 자식이 8개고 고려사항이 3개면 선택 한 번에 24번 점수 계산이다. 선택은 매 틱이 아니라 전이될 때만 일어나므로, 전이 빈도가 낮으면 감당할 만하다.

7. 줄이는 법

수단줄어드는 것
전이를 OnTick → OnEvent/OnDelegate매 틱 전이·조건 검사
bShouldCallTick 끄기 (이벤트만)태스크 Tick 과 바인딩 복사
CustomTickRate그 상태의 틱 빈도 (0.2초면 5배 적게)
수면 허용 (스키마 ScheduledTickPolicy)틱 자체. 이벤트 올 때까지 0
상위 상태에 태스크를 두지 않기경로 길이 × 태스크
비싼 계산을 Evaluator 로 몰기상태마다 중복 계산

가장 큰 절감은 OnTick 을 이벤트로 바꾸는 것이다. 매 틱 후보를 훑는 대신, 값이 바뀌는 순간 한 번만 반응한다. 폴링이 정말 필요한지 먼저 물어야 한다.

숫자를 볼 때는 AI 수 × 틱당 콜백 수로 먼저 어림한다. 50마리 × 9회 = 450회/틱이면 콜백 하나가 10µs만 되어도 4.5ms다. 여기서 태스크 Tick 을 끄거나 OnTick 전이를 이벤트로 바꾸면 바로 줄어든다.
