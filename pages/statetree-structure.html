StateTree ① — 상태 계층과 실행

StateTree 는 "지금 어떤 상태인가"를 계층으로 들고 있는다. 상태가 바뀔 때만 Enter/Exit 가 불리고, 그 사이에는 태스크가 계속 Tick 을 받는다. 이 페이지는 에셋 → 컴포넌트 → 컨텍스트 → 한 틱 순서로 실행 경로를 따라간다.

구조와 실행 노드 4종 전이와 선택

1. BT 와 무엇이 다른가

Behavior Tree 는 다음에 무엇을 할지를 매번 트리 위에서 다시 고른다. StateTree 는 지금 어떤 상태인지를 유지하고, 그 상태가 바뀔 때만 전이를 처리한다. 상태 하나가 "태스크 묶음 + 자식 상태 + 진입 조건 + 전이"를 함께 가진 단위다.

Behavior TreeStateTree
실행 단위노드(Task)상태(State)
유지되는 것ActiveNodeActiveStates 경로
분기 결정Composite 가 고른다Transition 이 지정
재진입매번 ExecuteTaskSustained 로 표시. 유지 중 Enter 는 태스크 플래그가 결정
데이터BlackboardInstanceData + 바인딩

그래서 StateTree 에는 BT 의 Sequence/Selector 같은 Composite 가 없다. 대신 계층이 순서를 만들고, 전이가 분기를 만든다. "Combat 안에서 Melee 냐 Ranged 냐"는 Combat 의 자식 선택 규칙(Selection Behavior)이 정한다 — ③ 전이와 선택.

2. 에셋과 컴파일

UStateTree 는 UDataAsset 이다. 에디터에서 만지는 트리(UStateTreeEditorData)는 런타임에 쓰이지 않는다. 저장할 때 평평한 배열로 구워지고, 런타임은 그 배열만 본다.

UStateTree (DataAsset) ├─ EditorData // 에디터 전용 └─ 컴파일 결과 ├─ Frames // 실행 프레임 ├─ States // 상태 (인덱스로 연결) ├─ Transitions // 전이 ├─ Nodes // 태스크·조건·평가자 ├─ PropertyBindings // 바인딩 배치 └─ DefaultInstanceData // 인스턴스 원본

에셋이 최신 컴파일 상태인지는 IsReadyToRun() 으로 본다. 에디터 데이터를 고치고 컴파일하지 않으면 런타임은 옛 배열을 계속 쓴다 — "에디터에서 고쳤는데 게임에서는 그대로"의 흔한 원인이다.

Schema(UStateTreeSchema)는 이 트리가 쓸 수 있는 노드 종류와, 실행할 때 반드시 있어야 하는 컨텍스트 데이터를 정한다. 스키마가 다르면 같은 트리를 다른 컴포넌트에 붙일 수 없다.

Schema쓰는 곳보장되는 컨텍스트
UStateTreeComponentSchemaUStateTreeComponentActor 하나 (지정한 ContextActorClass)
UStateTreeAIComponentSchemaUStateTreeAIComponentAIController + Actor(빙의된 폰)
직접 만든 스키마커스텀 컴포넌트GetContextDataDescs() 로 선언한 것

3. 컴포넌트

UStateTreeComponent 는 UBrainComponent 를 상속한다. BT 컴포넌트와 같은 두뇌 슬롯이라, 컨트롤러 입장에서는 "AI 두뇌가 BT 냐 StateTree 냐"의 차이다.

BeginPlay └─ bStartLogicAutomatically 면 StartLogic() └─ StartTree() ├─ HasValidStateTreeReference() ├─ FStateTreeExecutionContext(...) ├─ SetContextRequirements() │ // Actor / AIController └─ Context.Start(...) → bIsRunning
  • StateTreeRef 는 FStateTreeReference — 에셋 포인터 하나가 아니라 파라미터 기본값 오버라이드까지 함께 든다.
  • bStartLogicAutomatically 기본값은 true. 직접 시작하려면 끄고 StartLogic() 을 부른다.
  • StopLogic(Reason) 은 진행 중인 태스크에 Exit 를 보내고 멈춘다. 실행 상태가 바뀌면 OnStateTreeRunStatusChanged 가 브로드캐스트된다.
  • UStateTreeAIComponent 는 AIController 용이다. BT 안에서 BTTask_RunStateTree 로 서브트리처럼 돌릴 수도 있다.

4. 실행 컨텍스트

컴포넌트는 매 Tick 마다 FStateTreeExecutionContext 를 스택에 만들어 쓴다. 이 객체가 "이번 틱의 트리 실행" 그 자체다. 트리 상태(활성 상태, 인스턴스 데이터, 이벤트 큐)는 컴포넌트가 들고 있는 InstanceData 에 남는다.

용어누가 정하나없으면
Context DataSchema시작 자체가 실패한다 (Actor 를 못 찾으면 로그를 남기고 틱이 꺼진다)
External Data노드의 Link()링크 실패 → 트리가 실행 불가로 표시된다
InstanceData에셋의 기본값을 복사태스크 상태가 남지 않는다

Context Data 는 바인딩의 출발점이기도 하다. 스키마가 Actor 를 보장하니, 태스크는 "Actor 의 Health" 같은 경로를 바인딩할 수 있다. AI 스키마는 여기에 AIController 를 더한다.

5. 한 틱의 네 단계

FStateTreeComponent::TickComponent
  └─ FStateTreeExecutionContext::Tick(dt)
       ① TickPrelude()            // 외부 데이터 수집, 실행 중 확인
       ② TickUpdateTasksInternal  // 평가자 → 글로벌 태스크 → 상태 태스크
       ③ TickTriggerTransitions   // 전이 수집 → 우선순위 → Exit → 선택 → Enter
       ④ TickPostlude()           // 예약된 Stop 처리

②의 순서는 기본값(StateTree.TickGlobalNodesFollowingTreeHierarchy=1)에서 루트 평가자 → 루트 글로벌 태스크 → 상태 태스크 다. 링크된 서브트리가 있으면 그 평가자·글로벌 태스크·상태 태스크가 뒤에 이어 붙는다. 즉 데이터를 만드는 쪽이 먼저 돈다.

1.0×

해 볼 것. Melee → Ranged 로 바뀌는 순간을 보라. 부모 Combat 은 테두리가 점선(유지) 으로 남는다. 이때 아래 버튼을 꺼 보라 — 유지된 Combat 의 태스크가 EnterState 를 받는지(켬) 건너뛰는지(끔)가 상자 아래에 표시된다. Patrol → Melee 로 갈 때는 Combat 이 실선(새로 진입) 이 된다.

6. 활성 상태와 프레임

실행 상태는 두 층이다. ActiveStates 는 한 트리 안에서 루트→리프 경로이고, ActiveFrames 는 링크 때문에 생기는 바깥 층이다.

구조내용
FStateTreeExecutionFrame트리 하나의 실행 단위. Linked·LinkedAsset·Subtree 상태로 들어가면 프레임이 하나 더 쌓인다
ActiveStates그 프레임에서 지금 활성인 상태 경로. 마지막이 리프
EStateTreeStateChangeTypeChanged(새로 진입) / Sustained(상위라서 유지) / None

태스크는 EnterState/ExitState 에서 이 ChangeType 을 받는다. 여기서 많이 틀린다. Sustained 라고 Enter 를 안 부르는 게 아니다. 엔진은 Changed 이거나, Sustained 이면서 태스크의 bShouldStateChangeOnReselect 가 켜져 있을 때 EnterState 를 부른다. 이 값의 기본이 true 다.

// StateTreeExecutionContext.cpp — 상태 진입 시 태스크마다
bShouldCallEnterState =
    ChangeType == Changed
 || (ChangeType == Sustained && Task.bShouldStateChangeOnReselect);

그래서 기본 설정에서는 Melee → Ranged 로 바뀌어도 Combat 의 태스크가 EnterState 를 다시 받는다. 애니메이션 재생처럼 "들어갈 때마다 다시 시작"해야 하는 태스크에는 이게 맞다. 반대로 자원 점유나 등록처럼 한 번만 하면 되는 태스크는 이 스위치를 꺼서 유지 중 재진입을 막는다.

7. 한 틱에 전이가 여러 번 일어난다

전이 처리는 한 번 돌고 끝나지 않는다. ExitState → 상태 선택 → EnterState 를 마치고도 조건이 안 맞으면 같은 틱 안에서 다음 전이를 다시 본다. 반복 상한은 5회다.

// StateTreeExecutionContext.cpp — TickTriggerTransitionsInternal
for (int32 Iter = 0; Iter < MaxIterations /* 5 */; Iter++)
{
    if (TriggerTransitions())     // 후보를 모아 우선순위로 하나 고른다
    {
        ExitState(...);
        EnterState(...);          // 실패하면 다음 반복에서 새 상태를 고른다
    }
    if (상태가 Running && 브로드캐스트된 델리게이트가 없음) break;
}

그래서 "이벤트 하나로 상태가 두 단계 넘어갔다"는 일이 생긴다. 반대로 Enter 조건이 계속 실패하면 그 틱에는 상태를 못 정하고 다음 틱으로 넘어간다.

8. 수면 — 틱을 끄는 트리

모든 태스크가 bShouldCallTick 을 끄고 전이도 이벤트만 기다리면, 매 프레임 Tick 할 이유가 없다. 이때 컴포넌트는 자기 틱을 끈다. 이벤트나 완료 통지가 오면 다시 켠다.

  • ScheduleTickFrame — 다음 틱이 필요 없으면 SetComponentTickEnabled(false).
  • CustomTickRate — 상태별 틱 간격(초). 0 이면 매 프레임.
  • ScheduledTickPolicy — 스키마에서 수면 허용 여부를 정한다(기본값은 CVar StateTree.Component.DefaultScheduledTickAllowed).

수면은 최적화이자 함정이다. "Tick 에서 폴링하던 태스크"가 갑자기 안 불리면, 그 태스크는 이벤트로 깨워야 한다. 디버거에서 컴포넌트 틱이 꺼져 있는지부터 확인하는 이유다.

9. 디버깅

  • Gameplay Debugger (') — StateTree 컴포넌트의 활성 상태 목록(GetActiveStateNames)과 태스크 상태.
  • StateTree Debugger 창 — 실행 중 상태 전이·태스크 선택을 타임라인으로 본다.
  • stat StateTree — Tick·전이·상태 선택 비용.
  • LogStateTree — 컴포넌트가 남기는 경고(컨텍스트 실패, 스키마 불일치)가 여기로 온다.

가장 흔한 세 가지는 컴파일 안 됨, 컨텍스트 데이터 없음, 틱 꺼짐이다. 셋 다 에러 없이 "아무 일도 안 일어나는" 모습으로 나타난다.
